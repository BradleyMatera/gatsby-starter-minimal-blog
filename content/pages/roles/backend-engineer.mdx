## Core Responsibilities

A Backend Engineer is responsible for designing, building, and maintaining server-side logic, APIs, and data layers. Key responsibilities include:

- **API design and development:** Building RESTful endpoints with [Express.js](https://expressjs.com/) or [FastAPI](https://fastapi.tiangolo.com/) that handle CRUD operations, authentication, and business logic.
- **Database management:** Designing schemas, writing queries, and managing data with [MongoDB](https://www.mongodb.com/docs/) (document store) or [PostgreSQL](https://www.postgresql.org/docs/) (relational).
- **Authentication and authorization:** Implementing JWT-based auth flows ([Source](https://jwt.io/introduction)), refresh tokens, and role-based access control.
- **Deployment and hosting:** Deploying services to platforms like [Render](https://render.com/docs) with environment variable management and health check endpoints.
- **Testing:** Writing unit and integration tests with [Jest](https://jestjs.io/docs/getting-started) and [Supertest](https://github.com/ladjs/supertest) to validate API behavior.
- **Observability:** Adding structured logging, error tracking, and request tracing to diagnose issues in deployed services.
- **Documentation:** Maintaining READMEs, Postman collections, and API documentation so other developers can integrate quickly.

## Expanded Process Notes

### How I approach building a backend API

1. **Define the data model** — Start with the entities the API needs (users, posts, messages) and their relationships. For MongoDB, this means designing document shapes; for PostgreSQL, this means designing normalized tables ([Source](https://www.postgresql.org/docs/current/ddl.html)).
2. **Choose the framework** — For JavaScript projects, I reach for [Express](https://expressjs.com/) because it is minimal and well-documented. For Python projects, I use [FastAPI](https://fastapi.tiangolo.com/) for its automatic validation and OpenAPI generation.
3. **Implement auth early** — JWT-based authentication is added before business logic so every route can be protected. The JWT standard is defined in [RFC 7519](https://datatracker.ietf.org/doc/html/rfc7519) ([Source](https://jwt.io/introduction)).
4. **Write CRUD routes** — Each resource gets create, read, update, and delete endpoints with input validation and error handling.
5. **Deploy and document limitations** — I deploy to [Render](https://render.com/docs) and document cold start behavior, missing rate limiting, and other known gaps in the README.
6. **Test with Postman and Jest** — I maintain Postman collections for manual testing and write Jest + Supertest integration tests for automated validation ([Source](https://jestjs.io/docs/getting-started)).

### Common pitfalls I have encountered

- **Free-tier cold starts:** Render's free tier can take several minutes to wake a sleeping service. This is documented in every project README so reviewers are not surprised.
- **No rate limiting:** Without rate limiting, a deployed API is vulnerable to abuse. This is a known gap I am working to address with middleware like [express-rate-limit](https://github.com/express-rate-limit/express-rate-limit).
- **Unstructured logging:** Console.log without structured formatting makes debugging harder in production. Moving to structured JSON logging is a next step ([Source](https://expressjs.com/en/resources/middleware/morgan.html)).
