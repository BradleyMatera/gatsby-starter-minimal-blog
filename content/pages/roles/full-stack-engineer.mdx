## Core Responsibilities

A Full-Stack Engineer is responsible for building and maintaining both the frontend user interface and the backend services that power it. Key responsibilities include:

- **Frontend development:** Building responsive, accessible UIs with [React](https://react.dev/learn) and [Gatsby](https://www.gatsbyjs.com/docs/) for static site generation, or [Next.js](https://nextjs.org/docs) for server-rendered applications ([Source](https://react.dev/learn/start-a-new-react-project)).
- **Backend API development:** Building RESTful endpoints with [Express.js](https://expressjs.com/) or [FastAPI](https://fastapi.tiangolo.com/) that serve data to the frontend.
- **Database integration:** Connecting the frontend to databases like [MongoDB](https://www.mongodb.com/docs/) via backend APIs, managing data flow from UI to persistence layer.
- **Authentication flows:** Implementing end-to-end auth — login, registration, session management, and protected routes — using [JWT](https://jwt.io/introduction) tokens.
- **Deployment:** Deploying both frontend and backend to platforms like [Netlify](https://docs.netlify.com/), [GitHub Pages](https://docs.github.com/en/pages), or [Render](https://render.com/docs) with CI checks that validate builds.
- **Testing:** Writing unit, integration, and end-to-end tests with [Vitest](https://vitest.dev/) and [Playwright](https://playwright.dev/docs/intro) to validate behavior across the stack.
- **Accessibility:** Ensuring UIs meet [WCAG](https://www.w3.org/WAI/standards-guidelines/wcag/) accessibility standards with semantic HTML, ARIA labels, and keyboard navigation.

## Expanded Process Notes

### How I approach building a full-stack application

1. **Design the data flow** — Map out how data moves from the database through the backend API to the frontend UI. For Car-Match, this meant MongoDB documents → Express routes → React components.
2. **Build the backend API first** — I start with [Express](https://expressjs.com/) endpoints for CRUD operations and auth, so the frontend has something to call. JWT-based auth is implemented early using the [JWT standard](https://jwt.io/introduction).
3. **Build the frontend** — I use [React](https://react.dev/learn) for component-based UIs. For content-heavy sites, [Gatsby](https://www.gatsbyjs.com/docs/) provides static site generation with excellent performance. For app-like experiences, [Next.js](https://nextjs.org/docs) offers server-side rendering and API routes.
4. **Wire them together** — Connect the React frontend to the Express backend with fetch calls or API clients. Handle loading states, error states, and empty states in the UI.
5. **Add CI checks** — [GitHub Actions](https://docs.github.com/en/actions) runs linting, type-checking, and build validation before any deploy. Build failures block the deployment.
6. **Deploy and document** — Frontend goes to [Netlify](https://docs.netlify.com/) or [GitHub Pages](https://docs.github.com/en/pages); backend goes to [Render](https://render.com/docs). Known limitations (cold starts, missing tests, incomplete features) are documented in the README.

### Common pitfalls I have encountered

- **CORS issues:** When frontend and backend are on different domains, Cross-Origin Resource Sharing must be configured. The [cors middleware](https://github.com/expressjs/cors) for Express handles this, but it is easy to misconfigure.
- **Free-tier cold starts:** Render's free tier can take several minutes to wake the backend, which makes the full-stack app appear broken. Documenting this in the README sets correct expectations.
- **Inconsistent state management:** Without a clear state strategy, React components can get out of sync with the backend. Using React Query or a context-based approach helps ([Source](https://react.dev/learn/managing-state)).
- **Accessibility gaps:** Full-stack apps often neglect accessibility. Running [Lighthouse](https://developer.chrome.com/docs/lighthouse/overview/) audits and testing with keyboard navigation catches common issues.
