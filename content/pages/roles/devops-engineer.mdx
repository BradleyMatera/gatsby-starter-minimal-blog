## Core Responsibilities

A DevOps Engineer is responsible for automating build, test, and deployment workflows, and bridging the gap between development and operations. Key responsibilities include:

- **CI/CD pipeline design:** Building automated pipelines with [GitHub Actions](https://docs.github.com/en/actions) that run linting, type-checking, testing, and build validation before deploys ([Source](https://docs.github.com/en/actions/learn-github-actions/understanding-github-actions)).
- **Containerization:** Creating repeatable local development environments with [Docker](https://docs.docker.com/) and [Docker Compose](https://docs.docker.com/compose/) so onboarding and environment parity are easier ([Source](https://docs.docker.com/get-started/overview/)).
- **Deployment automation:** Configuring automated deploys to [Netlify](https://docs.netlify.com/), [GitHub Pages](https://docs.github.com/en/pages), or [Render](https://render.com/docs) with build-failure gates that block broken releases.
- **Infrastructure as Code (IaC):** Provisioning cloud resources with [Terraform](https://developer.hashicorp.com/terraform/docs) instead of manual console changes ([Source](https://developer.hashicorp.com/terraform/intro)).
- **Monitoring and observability:** Setting up logging, alerting, and dashboards to detect issues before users report them. Tools like [Prometheus](https://prometheus.io/docs/introduction/overview/) and [Grafana](https://grafana.com/docs/) are industry standards.
- **Secrets management:** Storing API keys and credentials securely using environment variables, [GitHub Secrets](https://docs.github.com/en/actions/security-guides/encrypted-secrets), or vault tools — not hardcoded in source.
- **Rollback and recovery:** Designing deployment strategies that support rollback when a release introduces regressions.

## Expanded Process Notes

### How I approach setting up a CI/CD pipeline

1. **Define the build stages** — Identify what needs to pass before a deploy: linting, type-checking, unit tests, and build validation. GitHub Actions uses YAML workflow files to define these stages ([Source](https://docs.github.com/en/actions/learn-github-actions/understanding-github-actions)).
2. **Add build-failure gates** — The pipeline should block deploys when any check fails. This prevents broken code from reaching production.
3. **Containerize the environment** — Use [Docker Compose](https://docs.docker.com/compose/) to define a repeatable environment with consistent Node, Python, or other runtime versions. This eliminates "works on my machine" issues ([Source](https://docs.docker.com/get-started/overview/)).
4. **Store secrets securely** — API keys and tokens are stored in [GitHub Encrypted Secrets](https://docs.github.com/en/actions/security-guides/encrypted-secrets), never committed to the repository.
5. **Add smoke tests** — After deploy, run basic checks (e.g., [k6](https://k6.io/docs/) load tests or Lighthouse audits) to verify the deployment is healthy.
6. **Document gaps** — README documentation lists missing health checks, rollback procedures, and manual steps so the limitations are transparent.

### Common pitfalls I have encountered

- **No rollback plan:** Without a rollback strategy, a bad deploy can take a site offline. Documenting a manual rollback process is a minimum first step.
- **Hardcoded secrets:** Storing API keys in `.env` files that get committed is a common mistake. Using [GitHub Secrets](https://docs.github.com/en/actions/security-guides/encrypted-secrets) for CI pipelines is the safe approach.
- **Missing health checks:** Without health check endpoints, deployment platforms cannot detect if a service is actually running. Adding a `/health` endpoint is a simple best practice ([Source](https://docs.docker.com/compose/startup-order/)).
