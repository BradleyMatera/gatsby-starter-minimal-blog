<Section id="overview" eyebrow="Problem" title="File uploads need a reliable metadata trail">
  <p>An object landing in storage is only the start of a workflow. Downstream systems need a consistent record of where the object lives, its type, size, checksum, and upload time. The processor also has to handle URL-encoded object keys, repeated event delivery, retries, and failed invocations without silently producing duplicate or missing records.</p>
  <p>The goal was to build that processing path with managed AWS services, keep the runtime small, and make the operational behavior inspectable through tests, alarms, and documented recovery procedures.</p>
</Section>

<Section id="approach" eyebrow="Architecture" title="S3 events become normalized DynamoDB records">
  <p>An Amazon S3 object-created event invokes a Python 3.12 Lambda function. The handler validates the event, URL-decodes the object key, and calls <code>HeadObject</code> to retrieve metadata without downloading or parsing the file body. It then normalizes that information into a DynamoDB record containing the bucket, key, size, content type, ETag, timestamps, and source details.</p>
  <div className="grid-two">
    <Card>
      <h3 className="feature-card__title">Event and data path</h3>
      <ol className="feature-list">
        <li>A file is uploaded to the configured S3 bucket.</li>
        <li>S3 publishes an object-created event to Lambda.</li>
        <li>Lambda validates the event and retrieves object headers.</li>
        <li>A deterministic SHA-256 record ID is generated from stable object identity fields.</li>
        <li>DynamoDB stores the normalized record using a conditional write.</li>
      </ol>
    </Card>
    <Card>
      <h3 className="feature-card__title">Why this design</h3>
      <ul className="feature-list">
        <li>No always-on application server to provision or maintain</li>
        <li>No file-body download when metadata alone is required</li>
        <li>Deterministic identity makes repeated event delivery predictable</li>
        <li>AWS SAM keeps infrastructure reviewable and reproducible</li>
        <li>Least-privilege IAM limits the function to the resources it needs</li>
      </ul>
    </Card>
  </div>
</Section>

<Section id="reliability" eyebrow="Reliability" title="Duplicate delivery and failures are designed into the workflow">
  <p>AWS event delivery is asynchronous, so retries and duplicates are normal operating conditions—not edge cases to ignore. The workflow creates a deterministic <code>RecordId</code> and uses DynamoDB's <code>attribute_not_exists(RecordId)</code> condition so a repeated event does not create a second metadata row.</p>
  <div className="grid-two">
    <Card>
      <h3 className="feature-card__title">Failure handling</h3>
      <ul className="feature-list">
        <li>Two asynchronous retry attempts</li>
        <li>One-hour maximum event age</li>
        <li>Encrypted SQS destination for exhausted failures</li>
        <li>Documented queue inspection and redrive procedure</li>
      </ul>
    </Card>
    <Card>
      <h3 className="feature-card__title">Operational visibility</h3>
      <ul className="feature-list">
        <li>CloudWatch alarms for Lambda errors and throttles</li>
        <li>An alarm for messages visible in the failure queue</li>
        <li>Optional SNS notifications for operators</li>
        <li>Structured logs with request and object identifiers</li>
      </ul>
    </Card>
  </div>
</Section>
